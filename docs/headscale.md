# Headscale variant (customer runs the control plane)

Headscale is an open-source, self-hostable implementation of the Tailscale
coordination server. The customer runs it themselves, which removes every
Tailscale-SaaS limit (device caps, ephemeral-minute metering, per-seat billing)
and puts the control plane under their control and in their region.

## The key point: zero code change

This is the SAME tailscale example. The runtime already forwards a login server:

```
tailscale up --authkey=$TS_AUTHKEY --login-server=$TS_LOGIN_SERVER ...
```

So switching from Tailscale SaaS to the customer's Headscale is purely env config:

- `TS_LOGIN_SERVER = https://headscale.customer.example` (their Headscale URL)
- `TS_AUTHKEY = <a Headscale pre-auth key>` (generated by `headscale` CLI)

The build extension, the userspace daemon, the middleware, the SOCKS routing:
all unchanged. Both the tasks and the customer's subnet-router / DB node register
to the customer's Headscale instead of Tailscale's servers.

## Customer-side setup (one-time)

1. Run Headscale on a small VM in their GCP project (ideally same region as the
   workers' peer, e.g. us-east4). It needs a public HTTPS endpoint.
2. Create a user and a pre-authorized, reusable, tagged auth key:
   ```
   headscale users create trigger
   headscale preauthkeys create --user trigger --reusable --expiration 720h
   ```
3. Define ACLs in the Headscale policy (same tag model: tag:trigger -> the DB
   node/subnet on 5432/8123).
4. Join the GCP-side node (the DB host or a subnet router) to Headscale with its
   own key, advertising the private route if it's a subnet router.
5. (Recommended) Run a DERP relay near the region, or use Headscale's embedded
   DERP, so the data path and handshake stay in-region.

## Why it helps here

- **Pricing:** removes the Tailscale device/ephemeral-minute limits entirely. Cost
  becomes just the Headscale VM (~$15-40/mo) plus optional DERP, regardless of how
  many concurrent worker nodes there are. This is the escape hatch for the large
  pricing bands.
- **Cold start:** the ~1s of the Tailscale cold start is the coordination-server +
  DERP handshake RTTs. With Headscale and a DERP in the customer's region (next to
  the workers' peer), those round trips shrink, so the handshake portion of cold
  start should drop. (The exact gain needs measuring against a live in-region
  Headscale; it does not change the client code.)

## Tradeoffs

- The customer operates Headscale: availability, upgrades, backups, DERP capacity.
- Some Tailscale features are reduced or absent on Headscale (parts of the admin
  UI, certain ACL/posture features, Tailscale SSH nuances). None of them are used
  by this pattern (userspace client + SOCKS + a single grant).
- No vendor SLA/support.

## Status

Documented and confirmed compatible with the existing runtime (TS_LOGIN_SERVER is
already wired). Not yet stood up against a live Headscale instance in this POC; a
live in-region Headscale test would quantify the cold-start improvement.
